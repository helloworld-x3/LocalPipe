# LocalPipe 完整参赛方案实施计划

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 在 2026 年 8 月 16 日前，将现有 LocalPipe 文本创译 MVP 打磨为一个有企业业务依据、可演示、可验证、至少落地一项飞书 AI 能力的完整参赛方案，冲击全国 40 强。

**Architecture:** 保留现有四层创译流水线作为核心质量引擎；以飞书多维表格作为任务、状态、审核反馈和结果展示层；对企业尚未确认的流程、数据和指标使用明确的“待确认假设”隔离，确认后再接入。最终交付由代码、飞书闭环、实验证据、参赛文档和 3—5 分钟 Demo 组成。

**Tech Stack:** Python 3、OpenAI 兼容模型接口、JSON 配置与结果文件、unittest、GitHub Actions、飞书多维表格/企业豆包/Aily/妙搭（按 Coach 确认选择）。

---

## 0. 工作原则

- 先验证企业业务，再扩展功能；不把命题推测写成企业事实。
- 先完成一个端到端闭环，再扩展市场、素材类型或模型数量。
- 所有新增能力都必须有可运行示例、失败处理和测试证据。
- 公开群问通用问题；企业流程、数据样例和差异化设计通过 Coach 私聊确认。
- 8 月 6 日前形成第一版方向材料，8 月 13 日前形成可评审候选稿，8 月 16 日完成提交。

## 1. 现状审计（8 月 2—3 日）

**目标：** 把当前 MVP 的真实能力、限制和证据整理出来，避免在 Coach 对接前凭印象改代码。

**输出：** `docs/current-state-audit.md`、可复现运行记录、待确认假设表。

### 任务 1.1：运行离线测试和示例

**Files:**
- Test: `test_pipeline.py`
- Run: `pipeline.py`、`batch.py`、`baseline.py`

**Steps:**
1. 在干净环境安装 `requirements.txt`。
2. 运行 `python -m unittest discover -v`，记录通过数量和失败项。
3. 运行三个市场的离线示例，保存命令、输入、输出和生成文件名。
4. 用不配置真实 API 的方式确认测试不会发起外部请求。
5. 记录当前不能声称的能力：母语者盲测尚未完成、飞书闭环尚未接入、图片/视频仍是后续边界等。

### 任务 1.2：建立能力—证据矩阵

**Files:**
- Create: `docs/current-state-audit.md`
- Inspect: `pipeline.py`、`model.py`、`batch.py`、`baseline.py`、`SECURITY.md`

**矩阵字段：** 能力、代码位置、输入、输出、失败状态、测试证据、Demo证据、是否需要企业确认。

### 任务 1.3：整理待确认假设

**必须列出：** 真实使用岗位、当前流程、创意输入格式、市场范围、审核人、返工点、业务量、验收指标、可提供的脱敏样例、飞书现有工具、数据与合规限制。

## 2. Coach 首轮沟通材料（8 月 3—6 日）

**目标：** 在 8 月 6 日前提交一份短而具体的问题汇总，不要求 Coach 替团队设计全部方案。

**输出：** `docs/coach-questions-v1.md`、一页项目现状卡、5—8 个最小代表样例。

### 任务 2.1：准备一页项目现状卡

包含：命题理解、当前 MVP 流程、核心差异化、已完成证据、当前边界、待企业确认问题、希望 Coach 给出的决策。

### 任务 2.2：准备首轮问题

按以下顺序提问：

1. 哪个岗位或团队使用本方案？
2. 创意从哪里进入，最终交付什么？
3. 最耗时和最容易返工的是哪一步？
4. 目前使用什么系统、表格或人工流程？
5. 企业如何判断本地化结果合格？
6. 能否提供脱敏输入、历史版本或失败案例？
7. 飞书多维表格、企业豆包、Aily、妙搭中，哪一个更容易落地？
8. Demo 是评审体验、录屏还是企业内部演示？

### 任务 2.3：建立事实状态标签

将每条信息标记为 `confirmed`、`assumption`、`unknown`，在 Coach 回复后更新；禁止把 `unknown` 写入最终方案的事实性描述。

## 3. 确定唯一核心业务闭环（Coach 首轮回复后）

**目标：** 从“多市场批量创译平台”收敛为一个评委能在 5 分钟内看懂、企业能验证价值的主流程。

**推荐闭环：**

```text
创意任务进入飞书任务池
→ LocalPipe 生成目标市场版本
→ 保真与文化风险检查
→ 结果回写飞书
→ 人工/市场审核评分
→ 反馈定位到画像或规则条目
→ 版本迭代并重新生成
```

**决策门：** 如果 Coach 证明企业实际流程不是以上链路，优先采用企业真实链路；不得为了保留现有代码强行套流程。

**输出：** `docs/confirmed-business-flow.md`、验收指标表、范围冻结清单。

## 4. 独立可做的工程增强（8 月 3—10 日）

这些工作不依赖企业内部数据，可先做；每项完成后必须补测试和运行证据。

### 任务 4.1：稳定运行与入口统一

**Files:** `pipeline.py`、`batch.py`、`model.py`、`README.md`

- 统一 CLI 参数、错误退出码和输出目录。
- 明确离线测试与真实 API 运行的边界。
- 为 Demo 准备一组固定脱敏样例和一条最短成功路径。

### 任务 4.2：结果可审计

**Files:** `pipeline.py`、`batch.py`

- 输出输入摘要、市场、画像版本、模型、时间、状态、失败原因、使用的画像条目和质检结果。
- 保持 `used_entries`、`skipped`、失败状态与实际输出一致。
- 不把模型自报分数当作唯一质量证据。

### 任务 4.3：实验与反例证据

**Files:** `docs/experiment-design.md`、`baseline.py`、`batch.py`

- 固定 A/B 配对规则。
- 准备 10 条中文创意 × 3 个市场的最小实验集。
- 执行可获得的人工/母语者评审；若无法完成，明确标记为限制，不虚构结果。
- 保留失败样例、needs_review 样例和人工修改前后对比。

### 任务 4.4：飞书协作闭环原型

**候选能力：** 优先多维表格；需要企业确认后再决定是否叠加企业豆包、Aily或妙搭。

- 建立任务字段：创意、目标市场、状态、输出链接、风险等级、审核意见、版本号。
- 明确 LocalPipe 与飞书之间是人工导入、文件导出还是 API/自动化连接。
- Demo 中至少展示“任务进入—结果回写—审核反馈”三步；无法取得 API 权限时使用可复现的导入导出方案，并如实说明。

## 5. 最终方案文档与 Demo（8 月 10—16 日）

**依据模板：** 参赛信息卡、场景痛点、创新点、具体方案、方案价值、体验入口/Demo、自由展示区、附录。

### 任务 5.1：完成事实版方案文档

文档必须回答：谁遇到什么问题、原流程如何、LocalPipe 如何介入、飞书承担什么、如何审核、价值如何测量、企业如何推广。

### 任务 5.2：制作 3—5 分钟 Demo

推荐节奏：

1. 20 秒：真实问题与输入。
2. 40 秒：飞书任务池与状态。
3. 90 秒：LocalPipe 四层处理和关键质检。
4. 50 秒：审核反馈、失败接管和版本迭代。
5. 30 秒：Before/After 与量化指标。
6. 20 秒：落地方式和推广边界。

### 任务 5.3：提交前验收

- 文档链接开启互联网可阅读。
- 体验入口、测试账号、打开说明和视频链接有效。
- 删除模板评分提示表。
- 所有量化结论有来源、样本或明确假设。
- 运行命令、代码版本、示例文件和截图可复现。
- 8 月 16 日 24:00 前提交表单，并保存提交凭证。

## 6. 暂不做的事项

- 扩展几十个国家或大量新素材类型；
- 大规模图片、视频、配音生产；
- 完整 SaaS、登录、计费和多租户；
- 安卓 App/小程序；
- 为了展示复杂而增加无业务价值的多智能体；
- 没有企业数据支持的精确 ROI 承诺。

## 7. 完成定义

只有同时满足以下条件，才可称为“完整方案候选稿”：

- 至少一个企业确认的真实业务流程；
- 至少一项飞书 AI 能力进入关键链路；
- 一个端到端 Demo 可复现；
- 有基线、样例、失败处理和量化证据；
- 文档覆盖四项评分维度；
- 所有未知项和限制已显式披露；
- 提交链接和视频在截止前完成验证。
